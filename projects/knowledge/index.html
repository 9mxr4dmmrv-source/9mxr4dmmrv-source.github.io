何のための仕組みか

生成 AI と作業すると、成果物は早くできる一方で、「なぜそうしたか」「前に何で失敗したか」が残りにくい。 このリポジトリの目的は記録そのものではなく、過去の経験を「型」に変えて、新しい問題に応用できる状態にしておくことである。 記録の対象は、就職活動・個人開発（Plassist）・学習など、6つのリポジトリでの作業にまたがる。

2026-09-24 時点で、生ログは79件（3ファイル・約4,800行）、型は12件（採用5・候補5・廃止2）。

設計の中心 — 層を分ける

層性質書き手
捕捉（inbox）一時置き場。雑でよい。処理後に空になる本人（チャット・音声）
生ログ（raw）追記専用。過去の記録は書き換えない。訂正は元の記述の隣に注記を足す本人＋Claude Code
型（playbooks）上書き更新。同じ型が別の文脈で2回以上再現されたら昇格する。1回の経験を一般則にしないClaude（承認は本人）
規約（CLAUDE.md）AI が毎回読むルール。長さに上限を置く本人と Claude

生ログは全部は読まれない前提なので無限に増えてよく、型と規約は毎回読まれるので上限が要る。 この2つを混ぜないことが、全体の不変条件になっている。

記録を作業に戻す経路

書いただけの記録は、次のセッションに読まれない。そこで、記録と作業の間を往復するコマンドを置いている。

  • /rec — 作業の終わりに、判断と理由・失敗と原因を生ログへ追記する
  • /recall — 新しい種類の作業を始める前に、型と過去の記録を引き、 その作業をするリポジトリの規約に固定する（書いた場所が、次に読まれる場所になるように）
  • /lint — 記録の中身を点検する（型の反証・昇格・相対日付・矛盾）
  • /audit — 仕組みの構造を独立に審査する（置き場の重複・肥大・経路の断絶）

記録の置き場の規約（どこに何を書くか）は1つのファイルにまとめ、6つのリポジトリから同じ正本を読むようにした。 サブエージェントには、渡したファイル以外を読ませない（default-deny）。評価役に設計意図や本人の心証が漏れると、 独立した評価が迎合に変わるためである。

実例: 構造の独立審査（/audit）の初回（2026-09-18）

機械的な点検 → 審査官（規約と点検結果だけを読むサブエージェント）→ 当否の判定、の3段で組んだ。 初回は6つのリポジトリを対象に、指摘40件（高8・中24・低8）のうち33件を採用して反映した。 その後、3つのリポジトリで実際に /recall を回すと、欠陥は審査の中ではなく、 審査結果を受け手に渡す経路に出た（受け手が審査書の本文を読めなかった）。これも記録し、経路を直した。

記録を意味で探す検索（RAG の検索部）— 2026-09-23〜24

なぜ作ったか

生ログは約30万字（2026-09-23 時点）で、Claude が文字列検索（grep）で読める規模ではある。 ただし月あたりの増え方が速い。また、言葉を思い出せないまま「前にも似たことがあった」と探す場面では、 文字列検索は言い換えを拾えない。そこで、意味で探す検索を最小の形で作り、効くかどうかを測った。

作ったもの

  • 分割: 記録の見出しごとに分け、長いものは項目の境で800字以下にする（78件 → 476断片）。各断片の頭に見出しを付ける
  • ベクトル検索: 日本語の埋め込みモデル cl-nagoya/ruri-v3-130m を手元の PC の CPU で動かす。記録を外部に送らないため
  • キーワード検索: 文字2-gram の BM25。日本語は単語の区切りが無いので、文字の並びで数える。ベクトル検索と比べる基準線
  • ハイブリッド: 2つの方式の順位を RRF（1/(60＋順位) の和）で統合する
  • 差分更新: 索引は本文のハッシュで管理し、2回目以降は新しい断片だけを埋め込む。最初の埋め込みは476断片で524秒

評価 — 問いを書く人が答えを知っていると、評価は甘くなる

最初は、Claude が記録を読んでから書いた17問で3方式を比べた。どの方式もほぼ満点だった。 しかし問いを書いた側が答えを知っているので、「言い換え」のつもりでも本文の語が残る。 そこで、本人が本文を見ずに16問を書き、答えも本人が決めて、評価し直した。

評価キーワードベクトルハイブリッド
1: Claude が本文を読んで書いた17問15／1615／1716／17
2: 本人が本文を見ずに書いた16問7／1510／1411／13
3: 2の問い＋答えを読んでいない AI が作った検索語10／1412／1511／15

各セルは「1位で正解が出た問いの数／5位以内に正解が入った問いの数」。

  • 1位で当たる問いは、16/17 から 11/16 に下がった。最初の評価の甘さが数字で出た
  • 本人の問いでは、キーワード検索（7問）よりベクトル検索（10問）が多く1位で当てた。ただし差は数問で、16問では傾向にとどまる
  • 答えを決めるとき、本人が記憶から選んだ答えが、16問中3問で別の記録にあった。見出しだけで決めず、本文と照合してから確定した

評価の設計で決めたこと

  • 答えは本人が決め、Claude は本文を照合して候補を出すだけにした。Claude が決めると、検索で見つかったものに答えを寄せるおそれがあるため。照合には検索の仕組み自体を使わなかった
  • 検索語を足す実験では、答えの記録を読んでいない別の AI（サブエージェント）に検索語を作らせた。 答えを読んだ Claude が書くと、答えの言葉が混じるため。問いの文と記録の形式の説明だけを渡し、記録そのものは読ませなかった

うまくいかなかったこと

  • 検索語に外れた推測が入ると、その語を含む別の記録を上位に引き上げた（ある問いで 5位 → 11位）
  • ハイブリッドがキーワード検索に引きずられた問いがあった（ベクトル2位 → ハイブリッド10位）。2方式を同じ重みで足しているため
  • 検索1回に約23秒かかる（1回の計測。大半はモデルの読み込み）

役割の分担

AI と作ったものなので、誰が何をしたかを分けて書く。

  • 本人: RAG を試す発案と着手の決定、本文を見ずに評価し直すことの選択、評価の問い16問の作成、答えの選択と確定、 検索語を答えを読んでいない AI に作らせる方式の選択。知識ベース全体では、何を記録し何を型にするかの承認
  • Claude（Claude Code）: 検索の設計（分割・モデル・BM25・RRF・差分更新）とコードの全部、最初の評価の17問、答えの候補の照合、結果の分析。 知識ベース全体では、コマンドと規約の文面の起草と保守

このページの範囲と限界: 検索は実験の段階で、日々の運用にはまだ組み込んでいない。 RAG のうち答えを生成する部分（G）は評価していない。評価の問いは16問で、方式の差は数問にとどまる。 記録の本文は非公開のため、このページには載せていない。数字は各コミットのメッセージと評価スクリプトの出力による（2026-09-23〜24）。
