Plassist の裏側
— 開発とグロースの自動化 —

このページはPlassistというアプリの機能紹介ではない。 プログラミング未経験から個人でアプリを作り、Claude Codeで開発とマーケティングの 両方を自動化していった過程についてのページ。

個人開発／React Native・Expo／App Store公開中・Google Play申請中

Plassistとは（1行）

立てた予定と実際に使った時間を並べて比較する時間管理アプリ。受験期に「願望で計画を立てては 崩壊させる」を繰り返していた原体験から、約4年越しにアプリとして実装した。 機能の詳細は割愛し、以下は開発とマーケティングの裏側に絞って書く。

動機の変遷

このプロジェクトの位置づけは、作り始めてから3回変わっている。

  1. 始まり: 自分の課題を解決したい／アプリを作ってみたい。 受験期からの原体験（願望ベースの計画が崩壊する）を解決するアプリを、 プログラミング未経験の状態から作ってみたいという動機で着手した。
  2. 次の段階: マーケティングとClaude Code自動化の実践的な学習材料。 公開しても誰にもダウンロードされない現実に直面し、マーケティングを独学。 並行して、開発とマーケティングの両方をClaude Codeでどう自動化するかを 試行錯誤する実践の場になった。以下に書くのはこの段階で作った仕組み。
  3. 現在: メタシステムの一端。 個人の知識ベース・計画管理・戦略検討の仕組み（knowledge・plan・ advisement）と連動させる方向にシフトしている。この接続の詳細は、 メタシステムを扱う別ページで書く（ここでは立ち位置の変化として触れるにとどめる）。

開発の自動化 — Claude Codeでの多エージェント体制

設計の核は「隔離が要る所（クリーンな調査・バイアスのない評価・ノイズの多い実装/デバッグ）だけを サブエージェント化し、意図を込める核（計画・戦略・文言）はメインセッションに残す」という分担。 対話が命の2つの工程（アイディア出し・学習）は、サブエージェントにせずメインで読む 「ペルソナ」（idea.md・learn.md）にしている。

回し方

  1. 発想 — idea.md。Claudeは案を出さず、質問で考えを引き出す ファシリテーター役に徹する。「なぜそれをやりたいか」「今できていないのはなぜか」を 一つずつ掘り下げ、最後に本人の言葉で一枚にまとめる。
  2. 計画 — design-rules-pg.md。変更を小さく検証可能な単位に分解し、 影響範囲と既存パターンを調べたうえで、実装に進む前に一度立ち止まって本人の合意を待つ。
  3. 実装 — pg-implementer（サブエージェント）。合意済みの計画を 最小差分で実装する。設計判断はしない。曖昧な点に気づいたら憶測で埋めず止まって報告する。
  4. 理解 — learn.md。実装された差分を、本人が自分の言葉で 説明できるまで、ソクラテス式に導く。「これは何をしていると思う?」とまず予想させ、 実際とのズレだけを埋める。答えを一気に開示しない。
  5. デバッグ — pg-debugger（サブエージェント）。再現→切り分け→ 最小修正の手順で直す。ノイズの多い調査ログをメインの会話から隔離する。
  6. 独立レビュー — pg-reviewer（サブエージェント）。 誰が・どんな意図で書いたかを知らない立場で、差分だけを見て辛口に評価する。

バイアスを消す設計（最も気を使った部分）

pg-reviewerには、設計意図を書いたファイル（design-rules-pg.mdなど）を 渡さない。理由はpg-reviewer.md自身に明記してある。

設計意図を書いたファイルは根拠にしない。仮に見えても無視する。判断が「設計通りか」に 引っ張られ、外からの素直な評価でなくなるため。

レビューは毎回新規のセッションで呼び、前回の指摘を引き継がせない。「さっき作った良いコード」と 持ち上げず、対象を中立に指すだけで依頼する。役割は「気持ちよく通すこと」ではなく 「欠陥を見つけるボトルネック」と明文化している。

実例1: Googleカレンダー同期の安全ガード

Googleカレンダーとの双方向同期機能を実装した際、安全ガードを2種実装した。 自己検証（diff照合・型チェック・実機テスト）を済ませたあと、設計意図を渡さない独立レビューを 2周かけたところ、自己検証では見逃していた安全設計の欠陥を2回とも検出して修正した。 「自分で書いて自分でチェックする」だけでは抜ける穴が、対象だけを見る独立審査で見つかった実例。

実例2: OTA配信事故と再発防止（2026-08-17）

5月にビルドしたバージョン（v1.0.12 build14）に対して、8月に検証目的で eas update --branch productionを直接叩いてしまい、依存ライブラリのバージョンが ズレたJSが配信された。TestFlightとApp Storeは同じproductionチャンネル・同じ runtimeVersionを見ているため、両方の実機で起動直後クラッシュが発生した。 eas update:roll-back-to-embeddedで復旧。

再発防止は2段で講じた。

  • 構造的対策: app.jsonのruntimeVersionを ネイティブ変更を自動検知する{"policy": "fingerprint"}に変更。ネイティブに 影響する依存が変わると自動でバージョンが変わるため、本体と噛み合わないJSはそもそも配信されなくなる （既存の配布済みビルドには遡って効かないため、次にビルドし直したタイミングから有効）。
  • 運用ルール: productionを検証目的で直接叩かない。 検証したいJS変更は必ずpreviewチャンネルに先に配信し、動作確認してから昇格する。 「実機でサッと試したいだけ」でもproductionを経由しない。

リポジトリの棚卸し

開発途中でReplitのテンプレートから移行した経緯があり、server/・shared/・ drizzle.config.tsなどが「旧テンプレートの名残で、どこからも参照されていない」ことを 明示的に棚卸しし、CLAUDE.mdに「読むのも触るのも不要」と書いて固定した。 死んだ配線（現状どこからも呼ばれていない画面・モジュール）も同様に名指しし、 「改修のついでに触らない・変更提案が必要になったら実行せず理由を添えて確認する」というルールを置いた。 これにより、後から参加するAIエージェント（自分自身を含む）が生きているコードと死んでいるコードを 毎回調べ直さずに済む。

マーケティングの自動化

開発と同じ「実行と独立評価を分ける」構造を、マーケティングにも適用した。 考え方はSTP（商品・顧客・競合を定義し、顧客が価値を置く点に競合がやっていない切り口で 差別化する）。ESで自分自身に適用したSTPを、今度はプロダクトに適用する形になっている。

回し方

  1. 分析 — mk-analyst（サブエージェント）。 marketing/dataの実データ（App Store Connect・Play Consoleのエクスポート）だけを根拠に、 獲得・維持・訴求のどこに課題があるかをfindings.mdにまとめる。施策は決めない。
  2. 発想 — idea.md。findingsを見ながら狙いを整理する。
  3. 施策設計 — design-rules-mk.md。打つ施策を優先度つきで並べ、 各施策がfindingsのどの課題への答えかを明示してから、本人の合意を待つ。
  4. 作成 — メインセッションでASO文言・スクリーンショット構成・LPを作成。 事実・数字はmarketing/dataから正確に引用し、創作しない。
  5. 独立評価 — mk-critic（サブエージェント）。 誰が・どんな狙いで作ったかを知らない初見のターゲットユーザーとして、辛口に評価する。 流暢さ・体裁は加点せず、「誰の何を解決するかが具体か」「次の行動が明確か」だけを見る。

実例1: リネームの実測効果

旧名「Logi」がLogitechの登録商標と衝突するリスクを特定し、「Plassist」へリネームした。 候補2件（Dailyplan・Tokilog）を実地検索で棄却した2回の失敗から、 「①J-PlatPat商標 ②ストア実地検索 ③Google検索」の3点確認フローを確立している。 アプリ名を「Plassist - 勉強計画の改善アプリ」に変更した前後（v1.0.8→v1.0.10）を App Store Connectの実データで比較すると、日平均DLは0.3→1.1（+267%）、 ページ閲覧→DL率は3.8%→14.9%（+292%）だった（2026/3/20〜4/17）。

実例2: ニッチキーワード戦略

競合が不在の検索キーワード「計画倒れ」に集中するニッチ戦略を採用し、App Store検索で1位を獲得した。 公開約3か月で累計70DL、月次3→20→41件と成長。ファネルは表示5,112→ページ閲覧655（12.8%）→ 初回DL70（閲覧比10.7%）。

実例3: 直近の分析（2026-08-19・mk-analystの実出力）

直近90日（2026-05-20〜08-17）のApp Store Connect実データをmk-analystが分析した結果、 期間合計でインプレッション→ページ閲覧（CTR）9.19%・ページ閲覧→DL（CVR）8.29%だった。 外部の一般的なベンチマーク（カテゴリ非特化の参考値）と比較すると、CTRはおおむね同水準だが、 CVRはベンチマーク目安（概ね25〜34%）のおよそ1/3〜1/4で、 自社データの中でも最も外部水準から乖離していた。この分析は 「プロダクトページに来た人に、何が伝わっていないか（訴求段階）」を伸びしろとして示唆している。

この分析には、絶対数の小ささ（DLは1日0〜2件）ゆえに月次比較は参考程度に留めるべきという留保、 スパイクの原因が特定不能である旨、検索キーワード別内訳や継続率が今回のデータには 含まれていない旨が、すべて明記されている。mk-analystは「無い数字を作らない」 「事実と推測を必ず区別する」というルールで動いている。

実例4: 誇張のチェック

ストア説明文の改訂案を作る際、「広告なし」「登録不要」「データは端末内保存」といった 安心材料の文言を書く前に、それぞれ実際のコードで裏取りしている （広告SDK・アナリティクスSDKがpackage.jsonに無い／ログイン画面が実装に無い／ サーバーAPI通信が無い、をそれぞれ確認）。 マーケティング文言も「事実に基づく」という規約をコードレベルで運用している。

この設計の元になっている考え方

「実行する役割」と「それを独立に判定する役割」を分け、判定側には設計意図を渡さない — このパターンは、Plassistだけでなく、就活のES作成（es-researcher／es-evaluator） でも同じ形で使っている。個人の知識ベース・計画管理と合わせた「メタシステム」全体の設計思想は、 別ページで詳しく書く予定。
