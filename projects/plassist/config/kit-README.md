# Plassist Claude Code キット — 使い方

狙い: 隔離が要る所（クリーンな調査・バイアスのない評価・ノイズの多い実装/デバッグ）だけを
サブエージェントにし、意図を込める核（計画・戦略・文言）はメインに残す。
対話が命の2つ（アイディア出し・学習）は、サブにせずメインで読むペルソナにする。

## 1. 置き場所
Plassist リポジトリのルートに置く:
```
plassist/
  CLAUDE.md              中立な約束事（戦略は書かない）
  design-rules-pg.md        コード設計方針（メインが設計時に読む）
  design-rules-mk.md        マーケ設計方針（同上）
  idea.md        あなたの考えを引き出すモード（メインで読む）
  learn.md                成果物を自分で説明できるまで導くモード（メインで読む）
  marketing/
    data/                指標の実データ（ASC / Play Console のエクスポート）
    findings.md          mk-analyst が書く分析結果
  .claude/
    agents/              フラットなワーカー群（一発・隔離）
      pg-implementer.md / pg-debugger.md / pg-reviewer.md
      mk-analyst.md / mk-critic.md
```
- 置いたら Claude Code を再起動し、`/agents` で5体が見えるか確認する。
- リポジトリで共有したいので agents は project 版（.claude/agents/）。
  全プロジェクトで使い回したいものだけ ~/.claude/agents/ に置く。
- モデルは frontmatter 指定済み（実装/分析/デバッグ=sonnet、レビュー/批評=opus）。
  単純な調べ物は built-in の Explore（haiku）に任せてトークンを節約する。

## 2. 回し方（プログラミング）
1. 発想　: 「idea.md に従って、次の更新で何をやるか一緒に整理して」
2. 計画　: 「design-rules-pg.md に従って設計して。方針が出たら一度止まって」→ 合意
3. 実装　: 「pg-implementer で、合意した変更を実装して差分を返して」
4. 理解　: 「learn.md に従って、その差分のキモを解説して」（あなたが手を動かす）
5. 修正　: バグが出たら「pg-debugger で、この症状を再現して直して」
6. 評価　: 「pg-reviewer で、この差分を正確性・安全性・整合の観点で辛口レビューして」

## 3. 回し方（マーケティング）
1. 分析　: 「mk-analyst で marketing/data を分析して findings.md に書いて」
2. 発想　: 「idea.md に従って、findings を見ながら狙いを整理して」
3. 設計　: 「design-rules-mk.md に従って施策を設計して。方針が出たら止まって」→ 合意
4. 作成　: メインで文言/構成を作る（ASO・発信・LP）
5. 評価　: 「mk-critic で、この成果物を初見ユーザー目線で辛口評価して」

## 4. 評価・レビューを独立に保つ（肝）
- 中立な文で頼む。「さっき作った良いコード/文言を評価して」と持ち上げない。対象を指すだけ。
- 設計の話（なぜこの実装/訴求にしたか）を委譲文に書かない。
- レビュー系は毎回新規で呼ぶ（resume しない）。前回を忘れた初見として絶対基準で見る。
- CLAUDE.md に戦略を書かない（全サブに漏れる）。戦略は design-rules-* に置き設計時だけ読む。
- さらに独立性を上げたいなら、レビューだけ別の Claude Code セッションで回す。

## 5. 学びを落とさない
- 実装/分析の後は必ず learn.md を挟む。理解しないまま次に進まない。
- レビューの指摘を逐条でそのまま直さない。本質と些末を自分で仕分け、根本を直す。
- 反復は2〜3回で打ち切る（一つの評価器への過学習を避ける）。

## 6. 安全（このワークフローの外に出すもの）
- ストア公開・リリース申請・署名鍵・課金・アカウント設定は Claude にやらせない。
  手順を出させて、実行は自分で。破壊的操作は CLAUDE.md でも止めている。
