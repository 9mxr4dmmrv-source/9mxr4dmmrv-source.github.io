Plassist の裏側
— 開発とグロースの自動化 —

プログラミング未経験から個人でアプリを企画・開発・公開し、Claude Codeで開発と マーケティングの両方を自動化していった記録。機能紹介は最小限にとどめ、 その裏側を中心に書く。

個人開発／React Native・Expo／App Storeで公開中・Google Play申請中

Plassistとは

立てた予定と実際に使った時間を並べて比較する時間管理アプリ。受験期に「実現可能性より 願望で勉強計画を立てては崩壊させ、自分を責める」を繰り返していた原体験から、 約4年越しにアプリとして実装した。

  • 予定（この時間に何をするか）と実績（実際に何をしたか）を1画面で並べて記録
  • ワンタップのタイマーで実績をその場で記録
  • 日・週・月・3か月・年単位で、カテゴリー別の時間配分を統計表示
  • 32色でカテゴリーを自由に分類（科目ごと、仕事とプライベートなど）
  • Googleカレンダーと双方向同期（端末のカレンダー連携経由）
  • 完全無料・広告なし・アカウント登録不要
  • 記録データは端末内に保存し、独自サーバーへは送信しない （Googleカレンダー同期を使う場合は、その予定データがGoogle側に渡る）

以下は、このアプリを支える開発とマーケティングの裏側に絞って書く。

動機の変遷

このプロジェクトの位置づけは、作り始めてから3回変わっている。

  1. 始まり: 自分の課題を解決したい／アプリを作ってみたい。 受験期からの原体験（願望ベースの計画が崩壊する）を解決するアプリを、 プログラミング未経験の状態から作ってみたいという動機で着手した。
  2. 次の段階: マーケティングとClaude Code自動化の実践的な学習材料。 公開しても誰にもダウンロードされない現実に直面し、マーケティングを独学。 並行して、開発とマーケティングの両方をClaude Codeでどう自動化するかを 試行錯誤する実践の場になった。以下に書くのはこの段階で作った仕組み。
  3. 現在: 個人の情報整理・意思決定を支える仕組み全体の一部へ。 自分の知識・計画・意思決定を横断的に管理するための個人用の仕組みを別途構築しており、 Plassistもその一部として位置づけ直しつつある。つまり「単体のアプリ」から 「自分自身の情報管理・意思決定を支える基盤の一角」へと役割が広がっている段階にある。 この仕組み全体の詳細は、別ページで改めて書く。

開発の自動化 — Claude Codeでの多エージェント体制

開発環境の変遷: Replit → Claude Code

最初のWeb版は、書店で見つけた本で存在を知ったReplit（ブラウザ完結の開発環境）上で、 書籍・公式ドキュメント・公式動画を独学しながら開発した。プログラミング未経験からここまでの 到達点としてはReplitのブラウザ内AIアシスタントが有効に機能したが、その後React Native/Expoで ネイティブアプリ化する過程で、ローカルgit＋GitHub（private）＋Claude Codeへ開発体制を移行した。 以下に書く多エージェント体制・独立レビュー・OTA配信の運用は、この移行によって初めて成立した。

移行の痕跡は今もリポジトリに残っている。server/・shared/・ drizzle.config.ts・.replitなど、Replit時代のテンプレートの名残は、 本体（client/）からは一切参照されていないことを確認したうえで、 「読むのも触るのも不要」とCLAUDE.mdに明記して残してある（詳細は後述）。

設計の核は「隔離が要る所（クリーンな調査・バイアスのない評価・ノイズの多い実装/デバッグ）だけを サブエージェント化し、意図を込める核（計画・戦略・文言）はメインセッションに残す」という分担。 対話が命の2つの工程（アイディア出し・学習）は、サブエージェントにせずメインで読む 「ペルソナ」（idea.md・learn.md）にしている。

回し方

  1. 発想 — idea.md。Claudeは案を出さず、質問で考えを引き出す ファシリテーター役に徹する。「なぜそれをやりたいか」「今できていないのはなぜか」を 一つずつ掘り下げ、最後に本人の言葉で一枚にまとめる。
  2. 計画 — design-rules-pg.md。変更を小さく検証可能な単位に分解し、 影響範囲と既存パターンを調べたうえで、実装に進む前に一度立ち止まって本人の合意を待つ。
  3. 実装 — pg-implementer（サブエージェント）。合意済みの計画を 最小差分で実装する。設計判断はしない。曖昧な点に気づいたら憶測で埋めず止まって報告する。
  4. 理解 — learn.md。実装された差分を、本人が自分の言葉で 説明できるまで、ソクラテス式に導く。「これは何をしていると思う?」とまず予想させ、 実際とのズレだけを埋める。答えを一気に開示しない。
  5. デバッグ — pg-debugger（サブエージェント）。再現→切り分け→ 最小修正の手順で直す。ノイズの多い調査ログをメインの会話から隔離する。
  6. 独立レビュー — pg-reviewer（サブエージェント）。 誰が・どんな意図で書いたかを知らない立場で、差分だけを見て辛口に評価する。

バイアスを減らす設計（最も気を使った部分）

pg-reviewerへの委譲文には、設計意図を書いたファイル（design-rules-pg.mdなど） へのパスを渡さない。理由はpg-reviewer.md自身に明記してある。

設計意図を書いたファイルは根拠にしない。仮に見えても無視する。判断が「設計通りか」に 引っ張られ、外からの素直な評価でなくなるため。

レビューは前回のセッションを再開せず、毎回ゼロから呼び、前回の指摘を引き継がせない。 「さっき作った良いコード」と持ち上げず、対象を中立に指すだけで依頼する。役割は 「気持ちよく通すこと」ではなく「欠陥を見つけるボトルネック」と明文化している。 ただしこれはツールでアクセスを遮断する仕組みではなく、あくまで運用上の約束事である。 さらに独立性を上げたい場合は、レビューだけ別のClaude Codeセッションで回す運用も検討している。

実例1: Googleカレンダー同期の安全ガード（2026-08-04）

Googleカレンダーとの双方向同期で、同期処理特有の壊れ方に対する安全ガードを3つ実装した。

  • ローカルの予定データが空・読み取り失敗のときは、削除の反映もローカルへの書き戻しも 両方スキップし、誤って全データを消さないようにする
  • PUSH側とPULL側の対応関係（所有権）が崩れていた場合、重複するイベントIDを両方から 取り除いて自己修復し、結果をUIにも伝える
  • 削除判定に使う日付キーが不正な値のとき、削除しない側に倒す（フェイルオープンで 誤削除しないよう不正値を検査する）

自己検証（diff照合・型チェック・実機テスト）のあと、設計意図を渡さない独立レビュー （pg-reviewer）を2周かけ、指摘の大半に対応した。なお、PULL側の0件ケースに 対するガードは再現条件が確立できておらず、次の実装単位に明示的に持ち越している （「やった」だけでなく「まだやっていない」も同じ粒度で記録している）。

実例2: OTA配信事故と再発防止（2026-08-17）

5月にビルドしたバージョン（v1.0.12 build14）に対して、8月に検証目的で eas update --branch productionを直接叩いてしまい、依存ライブラリのバージョンが ズレたJSが配信された。TestFlightとApp Storeは同じproductionチャンネル・同じ runtimeVersionを見ているため、両方の実機で起動直後クラッシュが発生した。 eas update:roll-back-to-embeddedで復旧。

再発防止は2段で講じた。

  • 構造的対策: app.jsonのruntimeVersionを ネイティブ変更を自動検知する{"policy": "fingerprint"}に変更。ネイティブに 影響する依存が変わると自動でバージョンが変わるため、本体と噛み合わないJSはそもそも配信されなくなる （既存の配布済みビルドには遡って効かないため、次にビルドし直したタイミングから有効）。
  • 運用ルール: productionを検証目的で直接叩かない。 検証したいJS変更は必ずpreviewチャンネルに先に配信し、動作確認してから昇格する。 「実機でサッと試したいだけ」でもproductionを経由しない。

リポジトリの棚卸し

開発途中でReplitのテンプレートから移行した経緯があり、server/・shared/・ drizzle.config.tsなどが「旧テンプレートの名残で、どこからも参照されていない」ことを 明示的に棚卸しし、CLAUDE.mdに「読むのも触るのも不要」と書いて固定した。 死んだ配線（現状どこからも呼ばれていない画面・モジュール）も同様に名指しし、 「改修のついでに触らない・変更提案が必要になったら実行せず理由を添えて確認する」というルールを置いた。 これにより、後から参加するAIエージェント（自分自身を含む）が生きているコードと死んでいるコードを 毎回調べ直さずに済む。

マーケティングの自動化

開発と同じ「実行と独立評価を分ける」構造を、マーケティングにも適用した。 考え方はSTP（Segmentation：市場を細分化し、Targeting：どの層を狙うか決め、 Positioning：競合との対比で自社の位置づけを定める）。自己分析で使っていたのと同じ枠組みを、 今度はプロダクトに適用する形になっている。

回し方

  1. 分析 — mk-analyst（サブエージェント）。 marketing/dataの実データ（App Store Connect・Play Consoleのエクスポート）を主な根拠に、 必要に応じて競合アプリのストア表現や一般的なベンチマークをwebで補足しながら、 獲得・維持・訴求のどこに課題があるかを分析結果としてまとめる。施策は決めない。
  2. 発想 — idea.md。分析結果を見ながら狙いを整理する。
  3. 施策設計 — design-rules-mk.md。打つ施策を優先度つきで並べ、 各施策が分析結果のどの課題への答えかを明示してから、本人の合意を待つ。
  4. 作成 — メインセッションでASO文言・スクリーンショット構成・LPを作成。 事実・数字はmarketing/dataから正確に引用し、創作しない。
  5. 独立評価 — mk-critic（サブエージェント）。 誰が・どんな狙いで作ったかを知らない初見のターゲットユーザーとして、辛口に評価する。 流暢さ・体裁は加点せず、「誰の何を解決するかが具体か」「次の行動が明確か」だけを見る。

実例1: リネームと、そのあとの実際の推移

App Store Connectには性質の異なる2つの指標体系がある。App Analyticsの 「インストール数」は、データ共有に同意したユーザーだけを対象にした推定値（母数が小さい）。 Sales and Trendsの「ユニット数」は、実際の取引に基づく数で、母数はこちらの方が大きい。 両者を混同していたことに気づき、以降はSales and Trendsの実データ（itunes_sales_chartの CSVエクスポート）を、月次の実績としては優先的に使うようにしている。

旧名「Logi」がLogitechの登録商標と衝突するリスクを特定し、「Plassist」へリネームした。 候補2件（Dailyplan・Tokilog）を実地検索で棄却した2回の失敗から、 「①J-PlatPat商標 ②ストア実地検索 ③Google検索」の3点確認フローを確立している。 リネーム前後（v1.0.8→v1.0.10。この間に他の変更も含む）をApp Analyticsの実データで比較すると、 日平均インストール数は0.3件→1.1件、ページ閲覧→インストール率は3.8%→14.9%へと伸びた （2026/3/20〜4/17）。競合が不在の検索キーワード「計画倒れ」に集中するニッチ戦略も採り、 App Store検索で1位になった。

その後の月次の実績を、Sales and Trendsのユニット数（App Store Connectの実データ）で見ると、 3月3件→4月23件→5月46件と伸びたが、6月は14件まで落ち込み（5月比70%減）、 7月20件・8月（19日換算）21件と緩やかな回復基調にある。初速の伸びがそのまま続くとは 限らないことを、自分の手元データで確認した形になる。

実例2: 直近の分析（2026-08-19・mk-analystの実出力）

直近90日（2026-05-20〜08-17）のApp Store Connect実データをmk-analystが分析した結果、 期間合計でインプレッション→ページ閲覧（CTR）9.19%・ページ閲覧→インストール（CVR）8.29%だった （この分析はApp Analyticsのインストール数ベースで、同期間のインストール数は71件。 同じ期間のSales and Trendsのユニット数は69件で、ほぼ近い水準だった）。 PlassistのApp Storeカテゴリ（Education）に絞った外部ベンチマーク（SplitMetrics調べの中央値6.75%） と比べると、CVRはカテゴリ中央値を上回っている。カテゴリ別の外部ベンチマークが 無いCTRについては、外部水準との比較は今回は行わず、自社データの90日推移を基準に見ている。

この分析には、絶対数の規模ゆえに月次比較は参考程度に留めるべきという留保、 スパイクの原因が特定不能である旨、検索キーワード別内訳や継続率が今回のデータには 含まれていない旨が、すべて明記されている。mk-analystは「無い数字を作らない」 「事実と推測を必ず区別する」というルールで動いている。

実例3: 誇張のチェック

ストア説明文の改訂案を作る際、「広告なし」「登録不要」「データは端末内保存」といった 安心材料の文言を書く前に、それぞれ裏取りしている。「広告SDK・アナリティクスSDKが package.jsonに無い」「ログイン画面が実装に無い」の2つはコードを直接確認し、 「サーバーへの実通信が無い」はCLAUDE.mdに棚卸し済みの事実として記載されているものを 根拠にした。マーケティング文言を、思い込みではなく確認済みの事実の範囲に収める運用をしている。

この設計の元になっている考え方

「実行する役割」と「それを独立に判定する役割」を分け、判定側には設計意図を渡さない — このパターンは、Plassist以外の個人プロジェクトでも一貫して使っている設計原則である。 個人の知識管理・計画と合わせた仕組み全体の設計思想は、別ページで詳しく書く予定。
